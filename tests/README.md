# Тесты CRM

Все тесты вынесены из src в эту папку. Конфигурации Vitest и Playwright находятся в корне проекта.

- unit: адаптер Supabase, маппинг DTO, точная версия, белый список полей, отказ без версии, конфликт без повторов, пагинация, бизнес-правила, фильтры/сортировка/debounce, крутилка и подтверждение удаления.
- database: все миграции в PostgreSQL/WASM. 75 сочетаний ролей/статусов, RLS, неизменяемая история, повтор seed, конфликт версии, переназначение и архивирование. Auth имитируется только в памяти тестового процесса.
- integration: настоящие Supabase Auth и PostgREST трёх пользователей. Чужие UUID/история, запреты CRUD исполнителю, прямой записи/повышения роли/подделки истории, авторы, цикл доработки, атомарность отказа, конкурентные запросы, переназначение, аудит и настройки регистрации.
- e2e: Chrome с реальным Supabase. Вход, ошибки, сессия/выход, фильтры, две роли исполнителей, CRUD, переназначение, полный цикл доработки, устаревшая форма, мобильное меню и переполнение.
- security: серверные ключи и service_role JWT в исходниках/сборке, исключение env из Git. Это дополнительная проверка, а не универсальный поиск всех возможных секретов.

Серверные списки дополнительно проверяются в database/server-lists.mjs и integration/server-lists.mjs: сочетания поиска/объекта/статуса/исполнителя, глобальная сортировка до выделения страницы, границы страниц, буквальный поиск `%`, ограничение параметров и RLS для строк, счётчиков, справочников и истории. Unit-тесты проверяют передачу параметров в RPC без локального преобразования порядка и скрытие всей панели пагинации при 0/1 странице.

В e2e/server-pagination.spec.ts создаются временные списки длиннее страницы: 12 задач, 11 объектов и история из 16 событий. Проверяются переходы, отсутствие повторов, возврат к первой странице после сортировки/фильтра, размер 10/20, скрытие панели при одной странице и ограничения исполнителя. Проверяются query-параметры реального RPC-запроса из браузера.

Запросы чтения проверяются как GET без тела, с фильтрами/сортировкой/страницей в query string. Unit-тесты проверяют кириллицу и специальные символы в поиске, отсутствие `undefined` в URL, чтение карточек и справочников; все семь изменяющих RPC остаются POST с JSON. Облачные проверки списков и истории используют GET. Браузер проверяет методы реальных запросов и query-параметры.

В navigation.spec.ts проверяются переходы по названию и стрелке из карточки объекта в задачи у постановщика и исполнителя. На production-сборке (`CRM_BASE_URL`) один JS-модуль намеренно получает 404: приложение должно один раз перезагрузиться, открыть задачу по сохранённому адресу и сохранить сессию. Unit-тесты chunk-recovery проверяют ограничение повторных перезагрузок, офлайн и недоступность sessionStorage. После деплоя дополнительно проверяется доступность хеша предыдущей сборки.

Требуются Node.js 22.12+ и Chrome. Команды: npm test, npm run test:db, npm run test:cloud, npm run test:e2e, npm run build, npm run test:secrets. Весь прогон: npm run test:all.

Облачные и браузерные проверки читают исключённый из Git .env.supabase. Паролей и ключей в тестовом коде нет. Облачная матрица рассчитана на 8 исходных активных задач. Браузерные проверки учитывают текущее количество строк и проверяют принадлежность задач вошедшему исполнителю; точные количества и границы страниц проверяются на собственных временных записях. Тестовые записи архивируются в finally, их история сохраняется для аудита. Для запуска использовать выделенный тестовый проект; исходные задачи/аккаунты должны оставаться доступны.

Права пользователей проверяются с publishable key и настоящими access token. Серверный ключ нужен только для чтения сохранённого аудита после архивирования.

Для проверки развёрнутого приложения задать CRM_BASE_URL=https://testsupabase.dmitriy-borisenko.ru и выполнить npm run test:e2e. Локальный Vite при этом не запускается. Отчёты и снимки создаются в output/qa; browser trace выключен, чтобы не сохранять вводимые доступы.

Локальная SQL-матрица не заменяет настоящий Auth/PostgREST, поэтому оба набора запускаются отдельно. Проверены критерии ТЗ, а не все возможные атаки и нагрузки. Владельца проекта с полным SQL-доступом RLS ограничить не может.
