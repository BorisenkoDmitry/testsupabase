# Тесты CRM

Все тесты вынесены из src в эту папку. Конфигурации Vitest и Playwright находятся в корне проекта.

- unit: адаптер Supabase, маппинг DTO, точная версия, белый список полей, отказ без версии, конфликт без повторов, пагинация, бизнес-правила, фильтры/сортировка/debounce, крутилка и подтверждение удаления.
- database: все миграции в PostgreSQL/WASM. 75 сочетаний ролей/статусов, RLS, неизменяемая история, повтор seed, конфликт версии, переназначение и архивирование. Auth имитируется только в памяти тестового процесса.
- integration: настоящие Supabase Auth и PostgREST трёх пользователей. Чужие UUID/история, запреты CRUD исполнителю, прямой записи/повышения роли/подделки истории, авторы, цикл доработки, атомарность отказа, конкурентные запросы, переназначение, аудит и настройки регистрации.
- e2e: Chrome с реальным Supabase. Вход, ошибки, сессия/выход, фильтры, две роли исполнителей, CRUD, переназначение, полный цикл доработки, устаревшая форма, мобильное меню и переполнение.
- security: серверные ключи и service_role JWT в исходниках/сборке, исключение env из Git. Это дополнительная проверка, а не универсальный поиск всех возможных секретов.

Требуются Node.js 22.12+ и Chrome. Команды: npm test, npm run test:db, npm run test:cloud, npm run test:e2e, npm run build, npm run test:secrets. Весь прогон: npm run test:all.

Облачные и браузерные проверки читают исключённый из Git .env.supabase. Паролей и ключей в тестовом коде нет. Они рассчитаны на 8 исходных активных задач, создают временные записи и архивируют их в finally. История тестовых записей сохраняется для аудита. Не запускать против реальных клиентских данных или одновременно с изменением исходных фикстур.

Права пользователей проверяются с publishable key и настоящими access token. Серверный ключ нужен только для чтения сохранённого аудита после архивирования.

Для проверки развёрнутого приложения задать CRM_BASE_URL=https://testsupabase.dmitriy-borisenko.ru и выполнить npm run test:e2e. Локальный Vite при этом не запускается. Отчёты и снимки создаются в output/qa; browser trace выключен, чтобы не сохранять вводимые доступы.

Локальная SQL-матрица не заменяет настоящий Auth/PostgREST, поэтому оба набора запускаются отдельно. Проверены критерии ТЗ, а не все возможные атаки и нагрузки. Владельца проекта с полным SQL-доступом RLS ограничить не может.
