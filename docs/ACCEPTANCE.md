# Критерии ТЗ

Основание — исходное ТЗ «Мини-CRM: Объекты и задачи» из предыдущего чата и план Supabase PDF. Обязательные функциональные требования и безопасность исходного ТЗ имеют приоритет.

## Функциональность

1. Две роли, несколько пользователей: постановщик видит всё, исполнитель только назначенные задачи/связанные объекты. Проверяются SQL, облачный API и оба исполнителя в браузере.
2. Объекты с названием/адресом и задачами: CRUD через RPC, ограничения удаления, поиск и карточка.
3. Все поля задачи: название, описание, объект, исполнитель, статус, автор и дата. Служебные поля формирует сервер; прямое изменение запрещено.
4. Только разрешённые переходы: 75 сочетаний ролей и статусов; полный цикл доработки в API и Chrome. Возврат без непустой причины запрещён, включая пробелы/NBSP.
5. История: кто, когда, из какого статуса в какой, комментарий. Отказ не добавляет событие; история видна участникам доступной задачи.
6. Все пять экранов и действия по ролям проверяются в Chrome; мобильное меню и отсутствие переполнения — отдельные проверки.

## Дополнительные требования к спискам

1. Поиск и все фильтры задач (объект, статус, исполнитель), поиск объектов и сортировка выполняются Supabase. Фронтенд передаёт параметры и отображает готовый результат без фильтрации, сортировки и нарезки массивов.
2. Задачи, объекты и история загружаются страницами, по умолчанию по 10 записей. Панель пагинации вместе с выбором размера скрыта, если доступно не более одной страницы. Фильтр, сортировка и размер страницы сбрасывают номер страницы.
3. SQL- и облачные тесты проверяют порядок до LIMIT/OFFSET, точные количества, совместную работу фильтров, неверные параметры и запрет anon. RLS действует на строки, JOIN, справочники и счётчики без раскрытия чужих задач.
4. Браузерные тесты используют данные длиннее одной страницы, проверяют сетевые параметры, отсутствие повторов, длинную историю и видимость пагинации у обеих ролей.

## Шесть требований безопасности

1. Все четыре таблицы имеют RLS и точные гранты. Прямой клиентской записи нет. Публичные RPC выполняются как SECURITY INVOKER; узкие привилегированные реализации находятся в private.
2. Прямое чтение чужого UUID/истории и изменение чужой задачи исполнителем запрещены.
3. Переходы проверяются внутри БД. Изменение задачи и история сохраняются атомарно.
4. Клиент не может вставить, изменить или удалить историю; дополнительный триггер блокирует UPDATE/DELETE. Архивирование сохраняет аудит.
5. Открытая регистрация и анонимный вход отключены, что проверяется через настоящий API Auth.
6. Во фронтенде только publishable key. Серверный ключ/пароль — в игнорируемом локальном env; database.txt, basedata.txt, env и файлы ключей исключены из Git/Docker-контекста. Исходники и сборка дополнительно сканируются.

## Уточнения PDF

- Версии миграций синхронизированы с фактической облачной историей.
- Вместо SQLSTATE 40001 применяется PT409/HTTP 409: PostgREST 14 зацикливает исходный код. Прикладной конфликт не повторяется автоматически. Официальный источник указан в README.
- Добавлены настоящие Auth/PostgREST и браузерные проверки к прежней локальной SQL-матрице.
- Архивирование, переназначение в любом статусе и одна компания на проект сохранены как явные допущения.
