# Контур — мини-CRM «Объекты и задачи»

Рабочая CRM строительной команды. Постановщики управляют объектами и задачами, исполнители выполняют свои поручения и передают результат на проверку. Данные хранятся в Supabase; доступ проверяет база данных.

Приложение: https://testsupabase.dmitriy-borisenko.ru

## Отчёт о выполнении

Дата отчёта: **5 ноября 2026 года**. Исходники приложения и история изменений — в ветке [main](https://github.com/BorisenkoDmitry/testsupabase/tree/main).

Основа работы — исходное тестовое задание «Мини-CRM: Объекты и задачи». Ниже отдельно описаны требования ТЗ, дополнительные запросы заказчика и технические решения при реализации.

### Выполнено по исходному ТЗ

**Роли и доступ к данным**

- Реализованы постановщик и исполнитель. Схема допускает несколько пользователей каждой роли.
- Постановщик создаёт, редактирует и удаляет объекты и задачи, назначает исполнителей, принимает результат или возвращает на доработку, видит все активные объекты и задачи.
- Исполнитель видит только назначенные ему задачи и объекты, в которых есть его задачи. Он может взять свою задачу в работу и отправить на проверку.
- Кнопки действий соответствуют роли пользователя и текущему статусу задачи.

**Объекты, задачи и история**

- У объекта есть название, адрес и карточка со списком задач и их статусами.
- У задачи есть название, описание, объект, исполнитель, статус, автор и дата создания.
- Реализованы все разрешённые переходы: создание в статусе «Новая», «Новая → В работе», «В работе → На проверке», «На проверке → Принята», «На проверке → На доработке», «На доработке → В работе».
- Другие переходы запрещены. Возврат на доработку требует непустого комментария.
- Каждая смена статуса сохраняет автора действия, время, исходный и новый статус, комментарий. История доступна обеим ролям в пределах их прав на задачу.

**Экраны и обязательная безопасность**

- Работают вход по email/паролю, список объектов, карточка объекта, карточка задачи и «Мои задачи» исполнителя.
- Все четыре таблицы CRM защищены RLS — правилами доступа внутри базы. Права действуют и при прямом обращении к Supabase без интерфейса.
- Исполнителю запрещено читать и менять чужие задачи и их историю.
- Переходы статусов проверяет база. Прямое изменение статуса через API таблицы запрещено.
- Клиент не может вставить поддельное событие истории, изменить или удалить существующее.
- Открытая регистрация и анонимный вход выключены; созданы настоящие тестовые аккаунты Supabase Auth.
- Серверный ключ и пароли отсутствуют во фронтенде и Git. Клиент использует публичный publishable key и сессию вошедшего пользователя.

**Материалы для сдачи**

- Опубликовано [работающее приложение](https://testsupabase.dmitriy-borisenko.ru).
- Подготовлены один постановщик, два исполнителя, 3 исходных объекта и 8 исходных задач во всех пяти статусах; исходная история содержит 21 событие.
- В [GitHub-репозиторий](https://github.com/BorisenkoDmitry/testsupabase) отправлены исходники, [SQL-миграции](supabase/migrations), seed и инструкции запуска. Версии файлов согласованы с облачной историей миграций.

### Добавлено по инициативе заказчика

Эти пункты следуют дополнительным сообщениям после исходного ТЗ.

**Выбор библиотек и организация разработки**

- Использованы TanStack Query для запросов и кэша, React Hook Form и Zod для форм и проверки полей, React Router с Suspense для страниц, shadcn/ui и Redux Toolkit.
- Проект организован по FSD; длинные страницы и компоненты разделены на составные части.
- Сначала подготовлен шаблон на моковых данных, затем выполнено переключение на настоящую базу и автоматический перенос исходных данных без ручного заполнения таблиц.
- Настроен Supabase MCP и установлены официальные навыки Supabase для работы агента. Это инструменты разработки; они не являются функциями пользовательской CRM.

React, TypeScript и Supabase уже требовались исходным ТЗ. Дополнительным выбором были конкретные библиотеки, FSD и поэтапный порядок разработки.

**Интерфейс и удобство работы**

- Оформление доработано по присланному визуальному референсу: светлые поверхности, синие акценты, геометричный шрифт Manrope, единые формы и панели. Убрана лишняя информационная панель на экране входа, исправлены отступы и выравнивание.
- Таблица задач переведена на TanStack Table. Добавлена сортировка по названию, статусу, исполнителю и дате.
- Добавлены поиск и совместимые фильтры по строительному объекту, статусу и исполнителю. По дополнительному запросу весь поиск, фильтрация, сортировка и разбиение списков на страницы перенесены в Supabase. Браузер отправляет параметры и отображает только возвращённую сервером страницу.
- В задачах, объектах и истории добавлена серверная пагинация: по умолчанию 10 записей, варианты 10/20/50. Панель переключения и выбор размера страницы появляются только при наличии более одной страницы. Изменение фильтра, сортировки или размера возвращает к первой странице.
- Количество записей, сводные показатели, счётчики карточек и порядок вариантов в фильтрах вычисляет база с соблюдением RLS. Сортировка применяется ко всему результату до выделения страницы; подсчёт и строки возвращаются одним SQL-запросом.
- Все запросы чтения CRM используют GET: списки, справочники и история вызывают RPC с `{ get: true }`, параметры передаются в query string; отдельные карточки и профиль читаются через GET Data API. Операции создания, изменения, архивирования и смены статуса используют POST с JSON.
- Поиск выполняется через `useDebounce` с задержкой 300 мс.
- Индикатор загрузки появляется после 300 мс ожидания. Готовые данные из кэша показываются сразу, чтобы уменьшить мигание интерфейса.

**Тесты, Git и размещение**

- По отдельному запросу подготовлены расширенные автоматические проверки и все тесты вынесены в каталог [tests](tests/README.md).
- Код отправлен в указанный заказчиком репозиторий `BorisenkoDmitry/testsupabase`.
- В `.gitignore` и `.dockerignore` дополнительно включены названные заказчиком `database.txt`, существующий `basedata.txt`, локальные env, файлы ключей и временные материалы. Перед отправкой проверен состав Git-коммита на секреты.
- Приложение собрано в Docker на сервере заказчика, запущено отдельным сервисом и подключено к поддомену `testsupabase.dmitriy-borisenko.ru`.
- Выпущен сертификат Let’s Encrypt; настроены автоматическое продление действующим Traefik и перенаправление HTTP на HTTPS.

Само наличие рабочего сайта, GitHub-репозитория и защиты секретов предусмотрено ТЗ. Дополнительными требованиями были конкретный репозиторий, собственный сервер, Docker, поддомен и отдельная папка тестов.

### Технические доработки и принятые решения

- **Безопасная запись:** вместо прямого редактирования таблиц клиент вызывает семь узких серверных функций. Они проверяют пользователя, роль, назначение, допустимость действия и поля запроса. Привилегированные реализации находятся в неэкспонируемой схеме `private`.
- **Атомарная история:** изменение статуса и запись события выполняются одной транзакцией. Неуспешное действие не оставляет частично записанных изменений.
- **Удаление с сохранением аудита:** объекты и задачи архивируются через `deleted_at`. Объект с активными задачами удалить нельзя. История сохраняется, её UPDATE/DELETE дополнительно блокирует триггер.
- **Переназначение:** разрешено постановщику в любом статусе без сброса статуса. Старый исполнитель теряет доступ к задаче и истории, новый получает доступ.
- **Роли и сессии:** бизнес-роль берётся из защищённого профиля, а не из редактируемых пользователем metadata. Обрабатываются изменение и истечение сессии, очищается кэш предыдущего пользователя.
- **Адаптер данных:** добавлены типы из установленной схемы Supabase, проверка ответов через Zod, преобразование полей в DTO и отмена устаревших запросов. Четыре read-only RPC возвращают страницы задач/объектов/истории и компактные справочники; они выполняются как SECURITY INVOKER и сохраняют правила RLS. Параметры сортировки ограничены белым списком, размер страницы — 100 записями.
- **Docker и HTTP:** контейнер работает от непривилегированного пользователя, с файловой системой только для чтения, без Linux capabilities и опубликованного host-порта. Добавлены healthcheck, CSP и защитные HTTP-заголовки. Контейнер получает только публичные параметры Supabase.

### Ограничения и то, что не добавлялось

- Один Supabase-проект обслуживает одну компанию; изоляция нескольких компаний не реализована.
- Принятую задачу нельзя открыть повторно — такого перехода нет в ТЗ. Её обычные поля постановщик может редактировать.
- Описание задачи необязательно. Допущения об архивировании и переназначении описаны выше.
- Перетаскивание колонок обсуждалось как возможность TanStack Table, но не реализовано. Сортировка реализована.
- Вложения, сроки, уведомления и самостоятельная регистрация не добавлялись: их нет в исходном задании.
- На момент проверки Security Advisor оставлял дополнительную рекомендацию включить проверку паролей по списку утечек; она остаётся выключенной. Открытая регистрация при этом закрыта.
- Проверены перечисленные требования и сценарии. Полный нагрузочный тест и независимый аудит всех возможных атак в этот объём не входили.

## Запуск

Node.js 22.12+ (проверено на Node.js 24), npm.

```sh
npm ci
cp .env.example .env.local
# Заполнить публичные VITE_SUPABASE_URL и VITE_SUPABASE_PUBLISHABLE_KEY.
npm run dev
```

Основной режим — `VITE_DATA_PROVIDER=supabase`. Серверный ключ не нужен приложению и запрещён в `VITE_*`. Локальный mock-адаптер сохранён для изолированных тестов; опубликованное приложение работает с настоящим Supabase.

## Возможности

- Вход по email/паролю, проверка и восстановление сессии, выход с очисткой кэша пользователя.
- Объекты: список, поиск, карточка, создание, редактирование, архивирование.
- Задачи: создание, назначение/переназначение, редактирование, архивирование, поиск и фильтры по объекту/статусу/исполнителю.
- Полный цикл: Новая → В работе → На проверке → Принята либо На доработке → В работе. Для возврата обязательна причина.
- История с автором, временем, статусами и комментарием; сохраняется после архивирования.
- Исполнитель видит только свои задачи и связанные объекты. Прямые обращения к Supabase подчиняются тем же правилам.
- Сортируемая таблица, адаптивное меню, состояния загрузки/ошибки/пустого списка и проверки форм.

## Стек

React 19, TypeScript, Vite, React Router, TanStack Query/Table, Redux Toolkit, React Hook Form, Zod, shadcn/ui, Tailwind CSS. Архитектура FSD: app → pages → widgets → features → entities → shared. Общий контракт CrmApi и типы, сгенерированные из Supabase.

## Безопасность и решения

- Постановщиков и исполнителей может быть несколько; роль хранится в profiles. Клиент не может изменить её или повысить права через metadata.
- Все клиентские изменения — семь узких RPC. Прямой INSERT/UPDATE/DELETE таблиц запрещён; RLS действует и без интерфейса.
- Переход и история записываются атомарно.
- Удаление логическое, аудит сохраняется. Объект с активными задачами удалить нельзя. Принятую задачу повторно открыть нельзя.
- Переназначение разрешено в любом статусе без сброса статуса; прежний исполнитель теряет доступ к задаче/истории.
- Один Supabase-проект — одна компания. Вложения, сроки, уведомления и мультиарендность не входят в ТЗ.
- Серверный ключ используется только локально для создания Auth-аккаунтов и доверенного чтения архивного аудита в тесте. Во фронтенд и Docker передаются только публичный URL и publishable key.
- env, database.txt, basedata.txt, файлы ключей, локальные отчёты и временные данные исключены из Git и Docker-контекста.
