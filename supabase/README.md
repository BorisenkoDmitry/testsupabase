# Supabase: установка базы

В рабочем проекте схема установлена, данные перенесены, Auth и прямой Data API проверены. Версии локальных миграций соответствуют фактической облачной истории MCP.

## Новый проект

1. Создать Supabase-проект, выключить открытую регистрацию и anonymous sign-ins, оставить email/пароль.
2. Применить все SQL-файлы migrations в порядке имён: схема, безопасность/RPC, защита auto-RLS, конфликт без повторов, серверный доступ к аудиту. Первые два файла содержат транзакции.
3. Оставить public в Exposed schemas; не открывать private и auth.
4. Скопировать demo.env.example в игнорируемый .env.supabase. Указать URL, secret key, publishable key и тестовый пароль от 12 символов.
5. Запустить node --env-file=.env.supabase scripts/supabase/create-demo-users.mjs. Скрипт не меняет существующие пароли, не отправляет письма, не назначает бизнес-роли через metadata.
6. Выполнить seeds/demo.sql: 3 профиля, 3 объекта, 8 задач, 21 событие. Несовпадающий повторный импорт останавливается, чтобы не затереть изменения.
7. Выполнить checks/setup-check.sql, npm run test:db и npm run test:cloud. Заполнить публичные .env.local и проверить интерфейс командой npm run test:e2e.

Миграции повторно к существующей базе не применять. Supabase CLI v3 по умолчанию использует локальную среду: перед hosted-операцией проверять проект и параметры через --help.

## Архитектура

profiles, objects, tasks, task_history защищены RLS. authenticated получает только SELECT. anon не получает доступа к таблицам и изменяющим RPC.

Семь public.crm\_\* RPC имеют SECURITY INVOKER и вызывают узкие SECURITY DEFINER реализации в private. Они проверяют auth.uid(), активность профиля, роль/назначение, поля, переход и версию. search_path закреплён, имена квалифицированы; private не экспонируется.

Историю нельзя вставлять, изменять или удалять через клиентский API; UPDATE/DELETE дополнительно блокирует триггер. Только доверенному service_role выдан SELECT истории для серверного аудита, включая архив. Браузер этот ключ не использует.

Конфликт версии — PT409/HTTP 409. Исходный PDF использовал 40001, который зацикливается в PostgREST 14. Исправляющая миграция обновляет все пять функций, проверяющих версию.

Удаление логическое; история сохраняется. Автор/дата/начальный статус/актор истории задаются сервером. Переназначать можно в любом статусе без сброса; прежний исполнитель теряет доступ.

Исходный seed можно восстановить: node scripts/supabase/export-mock-seed.mjs. Для старого браузерного снимка доступны --snapshot и --out. Пароли не экспортируются. Ключ администратора нельзя помещать в VITE\_\* или Git.

PDF описывает предыдущие имена файлов миграций и этап до подключения облака. Актуальные инструкции — README и порядок имён в migrations; тесты — ../tests.
